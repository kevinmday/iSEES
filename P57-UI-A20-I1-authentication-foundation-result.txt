P57-UI-A20-I1 — AUTHENTICATION FOUNDATION RESULT

1. Executive result

COMPLETE. A narrow backend authentication foundation now provides durable researcher
accounts, normalized unique login identities, password verification, expiring and
revocable server sessions, cookie restoration, CSRF-protected logout, and one typed
server-principal dependency. The new trust boundary never accepts a researcher ID
from a request header, query, or body. Authentication creates no Investigation or
research state. No frontend production file was changed.

2. Authentication strategy implemented or deferred

Implemented the A20-I0-recommended local email/password strategy. Passwords use
Python's established hashlib.scrypt implementation with a fresh 128-bit random salt,
N=16384, r=8, p=1, and a 256-bit derived key. Encodings are one-way and versioned by
their algorithm/parameter envelope. Login performs the same scrypt work against a
dummy hash when an account is absent, and returns the same INVALID_CREDENTIALS
response for an absent account and a wrong password.

Account recovery, email verification, and privacy/terms presentation are intentionally
deferred because A20-I1 is the backend session foundation and no production Front
Door UI is in scope.

4. Files modified

The API application mounts the authentication router and stable error handler. Its
credentialed CORS policy was narrowed from wildcard origins/methods/headers to an
explicit ISEES_CORS_ORIGINS allowlist, defaulting to the two local Vite origins, and
GET/POST/OPTIONS plus Content-Type, X-ISEES-CSRF, and X-Request-Id.

5. Account contract

ResearcherAccount has an opaque server-generated acct_<UUIDv4 hex> identity, display
email, normalized case-folded email, scrypt password hash, ACTIVE/DISABLED lifecycle,
and UTC created/updated timestamps. normalized_email has a database UNIQUE constraint.
Client responses expose only researcherId, email, and sessionExpiresAt. Passwords,
hashes, normalized identity, lifecycle internals, and database records are not
returned.

6. Session contract

The server issues a random opaque bearer secret paired with a server-generated
ses_<UUIDv4 hex> lookup identity. SQLite stores only SHA-256(secret), never the raw
256-bit bearer secret. Each row binds exactly one account and records created,
expires, revoked, and last-used timestamps plus a digest of the CSRF secret. Session
resolution atomically verifies identifier+digest, revocation, expiry, account state,
and updates last-used. Logout revokes the resolved active session.

7. Server-principal boundary

require_authenticated_principal in isees_uap/authentication/principal.py is the one
authoritative dependency. It resolves only the HttpOnly session cookie, verifies the
stored digest and session state, and returns typed AuthenticatedPrincipal with the
account identity, safe email, session identity, expiry, and internal CSRF digest.
Missing, malformed, unknown, expired, and revoked sessions all produce the stable
AUTHENTICATION_REQUIRED response. GET /api/v1/auth/session uses this boundary.
require_csrf_protected_principal composes it for state-changing authenticated routes.
There is no development principal or request-header fallback.

Existing investigation/candidate/research/STUDIO endpoints were not migrated in this
increment, as directed. Their pre-existing caller-authored principal behavior remains
outside the new account trust boundary and is scheduled for parent-authority
convergence.

8. Database and migration behavior

Authentication uses its own configured SQLite database (ISEES_AUTH_DB_PATH; default
runtime/authentication.sqlite3). Migration 001 creates researcher_account and
authenticated_session, foreign-key linkage, lifecycle/check/unique constraints, and
an account/expiry index. Migration history is applied under BEGIN IMMEDIATE with WAL,
FULL synchronous writes, busy timeout, foreign keys enabled, deterministic version
ordering, rollback on failure, and rejection of a database newer than the code.
Existing Investigation storage is not read or mutated by account creation or login.

9. Endpoint inventory

  POST /api/v1/auth/accounts — create an account and issue its initial session
  POST /api/v1/auth/sessions — authenticate credentials and issue a session
  GET  /api/v1/auth/session — restore the current safe researcher projection
  POST /api/v1/auth/logout — CSRF-check, revoke the active session, clear cookies

Stable domain errors use {error: {code, message, requestId}}. Validation errors retain
FastAPI's existing 422 convention and contain no stored account or credential data.

10. Cookie and CSRF behavior

The isees_session cookie is HttpOnly, SameSite=Strict, Path=/, and carries matching
Max-Age and authoritative UTC Expires values. The isees_csrf double-submit cookie has
the same scope/expiry but is deliberately readable by the client. Authenticated
mutations require X-ISEES-CSRF to equal that cookie and its server-stored digest.
Production is the default ISEES_AUTH_ENV and always sets Secure. Explicit development
or test environments disable Secure only for local HTTP. Unknown environment names
fail configuration rather than weaken production defaults. Logout deletes both
cookies using the same attributes after revocation.

11. Security properties

  - Account and session identifiers are opaque and server issued.
  - No caller-supplied researcher identity participates in authentication.
  - Passwords are never stored plaintext or reversibly encrypted.
  - Absent-account and wrong-password login responses are indistinguishable.
  - Raw bearer and CSRF secrets are absent from database rows.
  - Sessions are expiring, revocable, account-bound, and checked server-side.
  - Restore returns only the safe identity projection.
  - Invalid CSRF cannot revoke a session.
  - Cookie policy separates secure production from explicit local development.
  - Credentialed CORS is allowlisted rather than wildcarded.
  - Database constraints and immediate transactions protect identity/session integrity.
  - Authentication neither creates nor activates/imports/canonicalizes an Investigation.
  - A fresh account has zero default, fixture, canonical, Inbox, comparison,
    experiment, or author state.
  - No authentication code logs credentials, cookies, bearer secrets, or hashes.

15. Known limitations

This increment does not add rate limiting, email delivery/verification, account
recovery, password reset, MFA, session-list management, global account-session
revocation, or key-peppered session digests. SHA-256 is appropriate for digesting the
high-entropy random bearer secret; passwords use memory-hard scrypt. The fixed cookie
names are intentionally shared by the router and principal boundary. Deployment must
set ISEES_CORS_ORIGINS to its exact production frontend origins.
